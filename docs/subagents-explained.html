Pipi architecture / simple guide

How subagents work

The main Pipi agent can start small worker agents. Each worker receives a task and a limited set of tools. This page explains the system in clear, B2-level English.

1

Remove

What does “removes” mean?

It means “does not give this tool to the child agent.”

Pipi makes a list of tools before it starts a child. It takes some tool names out of that list. The child cannot see or use those tools.

The tool files are not deleted. The main Pipi agent can still use them. Only the child’s tool list is smaller.

2

The agent graph

The system has one coordinator and several leaf workers. A leaf worker finishes its own task, but it does not create another worker.

  • Dark box: coordinator
  • White box: worker
  • Arrow: task or result
3

The tool filter

Think about a key ring. The main agent has every key. Before a worker starts, Pipi removes the keys that could create or manage more agents.

Before the filter

  • read / write files
  • run shell commands
  • search code
  • subagent_spawn
  • subagent_wait
  • workflow
  • ask_user
FILTER →

Child’s tool list

  • read / write files
  • run shell commands
  • search code
  • subagent_spawn
  • subagent_wait
  • workflow
  • ask_user

The crossed-out tools still exist in Pipi. They are simply unavailable inside the child session.

4

One task, step by step

  1. Main Pipi writes a prompt. It gives the worker all information needed for one task.
  2. Pipi chooses a harness. The worker can use Pi, Claude, or Codex.
  3. The worker acts alone. It uses allowed tools, but it cannot start more workers or ask you a question.
  4. The result comes back. Main Pipi reads the result and decides the next action.
5

Who can do what?

Action Main Pipi Child subagent
See the full user conversation Yes No — it sees its task prompt
Use normal coding tools Yes Yes, according to its harness
Start another subagent Yes No
Run a multi-agent workflow Yes No
Ask the user directly Yes No
Return a result to the coordinator Receives it Yes
6

Why block nested agents?

A flat graph is easier to control. The main Pipi agent always knows how many workers exist and which task belongs to each worker.

It prevents three problems

  1. Runaway growth: one worker cannot create many more workers.
  2. Lost context: every task and result returns through one coordinator.
  3. Unclear cost: the system keeps a fixed limit of four active workers.

Nested agents are technically possible, but they need extra rules for depth, cost, permissions, and cancellation. This setup chooses the safer, simpler graph.
