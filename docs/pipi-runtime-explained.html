Pipi runtime / visual architecture guide

One launch. One process. Many agents.

You type pipi, but Pipi does not replace the Pi engine. It starts Pi with an isolated profile. Pi subagents then run inside that same configured process.

1

Pipi

What is Pipi?

Pipi is an isolated launcher and configuration profile for Pi.

The pipi command first chooses Pipi-owned settings and session folders. It then starts the existing Pi executable. The engine is Pi; the environment and resources belong to Pipi.

This is similar to opening the same application with a separate user profile. The application stays the same, but its settings, tools, authentication, and history can be different.

2

The launch path

The executable path changes only once, at the outer edge. After startup, Pipi uses Pi's in-process SDK instead of launching more command-line programs.

Settings and resources PI_CODING_AGENT_DIR=~/.pipi/agent
Conversation sessions PI_CODING_AGENT_SESSION_DIR=~/.pipi/sessions
3

Where a Pi child runs

A Pi child is not a new terminal process. The parent creates a fresh agent session inside the already running Pipi process.

Important language rule: in architecture notes, “Pi backend” names the SDK implementation. It does not mean the child silently switches back to the regular ~/.pi profile. When the root was launched with pipi, the backend resolves Pipi's active agent directory.
4

One nested task, step by step

  1. You start Pipi. The launcher selects isolated settings and starts Pi once.
  2. The parent spawns a child. The shared manager reserves capacity and requests an in-process Pi session.
  3. The child inherits the profile. Its resource loader reads the active Pipi agent directory, not a second command's defaults.
  4. The result returns in memory. The manager updates the shared tree and the existing TUI remains in control.
5

The right boundary

“Use Pipi” should mean “inherit Pipi's profile,” not “start another Pipi program for every child.”

Recommended

One Pipi process

pipi
└── Pi runtime + Pipi profile
    ├── main session
    ├── child session
    └── nested child session

One manager can enforce depth and concurrency. One TUI can show the complete tree. Parent shutdown can clean up every child.

Avoid

A Pipi process per child

pipi
├── exec pipi for child A
└── exec pipi for child B

Each process would have its own manager, limits, lifecycle, and screen state. The root TUI could not reliably navigate or cancel the full tree.

6

What is shared, and what is separate?

Part Main and Pi children Reason
Operating-system process Shared Children use the in-process SDK.
Pipi agent directory Shared The resource loader resolves the active Pipi profile.
Manager and concurrency budget Shared — planned Safe nesting needs one tree-wide capacity limit.
Conversation context Separate Each child receives its own bounded task and transcript.
Session file Separate A child can be inspected without mixing its transcript into the parent's session file.
Interactive TUI Owned by main Children are headless; the root TUI presents and navigates their state.
7

Current behavior versus the plan

Already true

  • The pipi launcher selects isolated folders.
  • The launcher executes the existing Pi runtime.
  • Pi subagents use createAgentSession().
  • Child resource loading calls getAgentDir(), which resolves the active Pipi directory.
  • The main blocking wait tool is hidden from agents.

Planned in issue #1

  • Nested descendants use the same root manager.
  • One concurrency limit covers the complete tree.
  • Results move to the immediate parent without waiting.
  • Nested policy initially permits only the Pi backend.
  • The TUI shows parent, child, and sibling relationships.
No extra child installation command is required for this plan. The setup step remains npm run install:pipi, followed by launching the root session with pipi.
