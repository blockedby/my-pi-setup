01 / короткий вывод

Если Luna больше не кодит — одного feature недостаточно.

Feature

Luna пишет

Задачи графа, устранение конфликтов, ремонт интеграции и исправления после аудитов. Astra тоже может править код на финальном review.

Small feature

Luna пишет

Один постоянный исполнитель делает всю реализацию и затем исправляет замечания четырёх аудиторов.

Plan / Audit

Можно оставить

Luna собирает материал и проверяет. План синтезирует Astra. Audit-executor запускает проверки, но не должен исправлять исходники.

Предложение: остановить новые запуски текущего feature, отдельно решить судьбу small-feature и профиля luna-worker. Сохранить Luna как исследователя и аудитора. Не переписывать старую машину исполнения, если от неё всё равно отказываемся.

Ниже «сейчас» означает поведение и контракты прочитанного кода. «Предлагаю» — изменение, которого ещё нет. Это не полный проверочный аудит всех ветвей контроллера и не доказательство корректности runtime.

02 / три разных механизма

Субагент ≠ workflow ≠ pipeline

Механизм Кто строит процесс Как исполняется Что возвращает
Прямой субагент
subagent_spawn 		Главный агент задаёт одну задачу, профиль либо harness/model. Отдельный контекст, Pi / Claude / Codex. Фоновый запуск. Нет доступа к текущему разговору, рекурсивному делегированию и вопросам пользователю. ID сразу; автоматическое сообщение по завершении. Есть check/list/cancel. Интеграция результата остаётся у родителя.
Программный workflow
workflow 		Главный агент пишет JavaScript: фазы, agent(), parallel(), ветвления по результатам. Скрипт в ограниченном процессе; агентам доступны обычные trust-зависимые ресурсы. Результат agent() — объект с ok/output/structured/error, а не выброс исключения. По умолчанию блокирующий вызов; есть background. Артефакты сохраняются, возобновления нет.
Фиксированный pipeline
pipeline_run 		Контроллер и прописанные роли. В feature Astra дополнительно строит граф реализации. Фиксированные модели и права, этапы, проверка отчётов, контролируемые переходы. Фоновый запуск. ID сразу, автоматический итог; check/list/cancel и чтение артефактов. Состояние привязано к сессии, durable resume нет.

Важная граница: sandbox workflow ограничивает управляющий JavaScript, а не автоматически весь shell каждого дочернего агента. Профиль прямого read-only субагента тоже не равен файловой sandbox: в нём запрет изменений задаётся инструкцией при обычном наборе инструментов.

У workflow максимум 8 одновременных agent-вызовов и 32 вызова за запуск; первый ответ каждого ожидается до 45 секунд. Общего дедлайна нет; отдельный инструмент — обычно до трёх минут. Доступ к workflow по инструкции главного агента — только по запросу workflow или слову ultracode.

03 / модели и прямые профили

Имя модели не определяет её работу.

В коде фиксированы openai-codex/gpt-6-astra, gpt-5.6-sol, gpt-5.6-luna и gpt-5.6-terra того же провайдера. Роль и thinking level назначаются отдельно.

Профиль / модель Назначение Уровень Прямая квота
luna-explore Исследование; инструкция запрещает изменения файлов и внешнего состояния. Luna / max 16 на Luna, вместе с другими прямыми Luna
luna-worker Узкая реализация и тесты. Нельзя коммитить, пушить или менять внешнее состояние. Luna / max Та же общая квота 16
terra-audit Ручная глубокая read-only эскалация. Автоматически в пайплайнах не используется. Terra / high 8

Claude + Codex Прямые агенты в отдельных harness. Без профиля harness обязателен. По параметру / backend Общая 4

Эти квоты не применяются к pipeline. Его корни, аудиторы и задачи графа не занимают слоты прямых субагентов. Несколько pipeline могут работать параллельно. Лимит workflow — отдельный механизм.

Профиль фиксирует harness, model и reasoning; передавать их вместе с профилем нельзя. Прямой luna-worker/max и feature-исполнитель Luna/high — разные конфигурации, хотя модель одна.

04 / feature-pipeline — текущий, ещё не deprecated

Планирует Astra. Исполняют Luna. Потом ещё два аудита.

Главная сложность здесь не число публичных параметров. Это собственный runtime ветвей, коммитов, попыток, проверок, слияний и доказательств выполнения.

Вход: task, pipeline_name, подготовленный linked working_dir, явный git_commit=true, существующий абсолютный worktree_root, явный worktree_prepare. Нужны Linux/bubblewrap, чистые исходники, собственная attached-ветка, стабильный HEAD; ignored зависимости и сборки допустимы.

  1. 1. Discover 5 × Luna / medium

    Пять независимых исследователей; все отчёты должны пройти проверку контроллера.

    discover-problemПроблема и контекст задачи; разрешён shell для read-only gh по связанным GitHub задачам.
    discover-outcomeНужный результат и признаки успешности.
    discover-contextИнструкции репозитория, устройство проекта и существующие команды проверки.
    discover-user-scenariosПользовательские сценарии.
    discover-product-precedentsУже существующие решения и продуктовые образцы.

    Readiness gate: discover-context предъявляет команду и точный источник. Контроллер запускает её в подготовленном worktree. Без успешной проверки или при упавшей команде планирование не начинается.

  2. 2. Plan — независимые варианты 2 × Astra / low

    feature-plan-minimal ищет минимальное полное решение; feature-plan-robust — устойчивое решение с учётом конкретных рисков. Одинаковые исходные данные, чужой вариант не видят. Нужны оба валидных отчёта.

  3. 3. Plan — общий план и граф 1 постоянная Astra / low

    feature-plan-finalizer сначала синтезирует canonical plan, следующим ходом — execution graph. До review только читает. Это та же сессия, которая позднее проверит интеграцию.

    Граф не произвольный DAG: только структурируемые последовательности и fork/join. Перекрёстные зависимости до общего join запрещены. Task IDs задают стабильный порядок; пересечение ожидаемых writePaths само по себе граф не запрещает.

  4. 4. Build — задачи и ветви свежая Luna / high на попытку

    Задача получает подробную капсулу: цель, контекст, инварианты, инструкции, эскиз реализации, критерии и команды проверок. Всего до четырёх попыток; следующая сессия продолжает ту же ветку, грязные файлы и provisional commit.

    Последовательные задачи переиспользуют ветку; fork создаёт дочерние worktrees. Подготовка выполняется один раз для новой ветви, затем baseline-проверки. Сбой подготовки не расходует модельные попытки — он останавливает ветвь.

    Git делает контроллер: агент вызывает diff/check/finalize. Finalize выбирает точные commitPaths, создаёт или amend-ит один provisional task commit, чистит остатки и запускает обязательные проверки. Пустой список может означать проверенное отсутствие нужных изменений, но не разрешает молча выбросить значимые правки.

  5. 5. Build — join и ремонт контроллер + Luna / high при сбое

    Контроллер ждёт все дочерние результаты и cherry-pick-ит коммиты в стабильном порядке. Конфликт разрешает отдельная Luna через контролируемую финализацию. После join повторяются baseline checks; семантический сбой создаёт внутреннюю join-repair задачу с четырьмя попытками.

    Независимые ветви могут продолжаться во время исправимой неудачи. Терминальная ошибка прекращает новые старты, но уже выполняющийся сосед может закончить и сохранить фактический результат.

  6. 6. Review та же Astra / low

    Astra сверяет объединённый код с собственным canonical plan. Теперь может сама исправлять код через task-инструменты и один review commit. Обязательные review checks должны пройти. Второй граф реализации не создаётся.

  7. 7. Audit → audit-resolve корень Luna / xhigh + 4 × Luna / medium

    Создаётся отдельный постоянный корень аудита и исправлений. Он запускает четыре статических трека: результат, логика, функциональность, надёжность. Затем сам правит код или аргументированно отклоняет замечания, запускает проверки и может делать обычные remediation commits.

    Для отказавшего предварительного аудитора допускается один retry той же сессии либо одна замена, только если сессия не была создана.

  8. 8. Final-audit 5 contributors + 1 synthesis / Luna medium

    Общий audit segment: четыре статических аудитора, один executor с shell, один постоянный синтезатор. Контекст — требования, текущий diff и проверки; предложения планировщиков, транскрипты задач и история конфликтов скрыты от независимого аудита.

  9. 9. Final-resolve → complete тот же корень Luna / xhigh

    Корень исправляет или отклоняет каждое финальное замечание. На каждый finding ID нужен результат fixed/rejected, основания и данные проверки. После этих исправлений нового аудита нет. Контроллер добавляет Git-факты и итоговые артефакты. Completion — не разрешение на merge/deploy.

Цена в сессиях: по описанному графу без ошибок — 19 фиксированных модельных сессий плюс N задач реализации: 5 discovery + 2 кандидата + 1 Astra finalizer + 1 Luna remediation root + 4 предварительных аудитора + 6 final-audit. Повторные ходы существующей сессии сюда не прибавляются; новые попытки задач и repair-сессии увеличивают число. Это не измерение стоимости или задержки провайдера.
05 / small-feature-pipeline

Простой граф, но тоже Luna-кодер.

  1. Build корень + исполнитель / Luna medium

    Read-only координатор запускает ровно одного постоянного implement-small-feature. Тот исследует репозиторий, пишет код, тестирует и возвращает структурированный отчёт.

  2. Final-audit 4 × Luna / medium

    Четыре параллельных статических аудитора получают задачу, отчёт исполнителя и Git diff. Отдельного executor и синтезатора нет.

  3. Final-resolve → complete тот же исполнитель

    Все отчёты возвращаются в прежнюю сессию исполнителя. Один проход исправлений или аргументированных отклонений, проверки и фактический итог. Нет повторного аудита, замены исполнителя или повторного запуска аудиторов.

Итого: шесть сессий. Вход — подготовленный отдельный linked worktree; разрешение коммитов опционально, по умолчанию выключено. Коммитить может только исполнитель. Дополнительные feature-требования clean HEAD / bubblewrap / внутренних worktrees не применяются как тот же admission-контракт.

Последствие решения: оставить этот pipeline без изменений и одновременно запретить Luna кодить нельзя. Его нужно тоже отключить либо отдельно изменить модель исполнителя; здесь такая замена не сделана.

06 / plan-pipeline

Шесть исследователей → один автор плана.

discover-requirements-boundariesТребования и границы; read-only gh через bash.
discover-architecture-responsibilitiesАрхитектура и разделение ответственности.
discover-contracts-invariantsКонтракты и инварианты.
discover-reuse-simplicityПовторное использование и простота.
discover-quality-operationsКачество, эксплуатация, проверки.
discover-external-evidenceВнешние источники; единственный plan-трек с web search/fetch.

  1. Discover 6 × Luna / medium

    Контроллер запускает исследования параллельно. Каждый возвращает один отчёт своей роли. До получения всех валидных отчётов синтез не начинается.

  2. Synthesize 1 × Astra / low

    Astra получает задачу, отчёты и provenance; может читать локальные файлы через read/fd/rg. Нет shell, generic write, оркестрации или аудита. Отдаёт свободный Markdown через pipeline_plan_submit.

  3. Complete контроллер

    plan_path: null — полный план в итоговом сообщении, без записи. Путь — атомарная запись внутри working_dir. Существующий обычный файл может быть заменён. Структуру Markdown по заголовкам, волнам или «правильным словам» не валидируют.

Итого: семь сессий. Нет реализации, общего audit segment, финального реаудита или Git-решения. Поэтому текущий plan-pipeline нельзя представлять как «план прошёл независимый аудит» только по названию инструмента или старым инструкциям.

Найденный след старой модели: в controller.ts итоговый checks-текст всё ещё говорит «One Luna/xhigh synthesis session accepted the plan», хотя rootModel и фактический запуск plan — Astra/low. Это несогласованность отчётной строки, не доказательство запуска Luna вместо Astra. В рамках этой раскладки не исправлялась.
07 / audit-pipeline и общий audit segment

Пять независимых источников. Один накапливающий вывод.

audit-feature-outcomeРешена ли исходная задача, соблюдены ли критерии.
audit-logic-invariantsЛогика, состояния, инварианты.
audit-functional-correctnessКорректность поведения и крайние случаи.
audit-reliability-regressionsНадёжность и регрессии.
audit-executorЧитает scripts/manifests, запускает существующие безопасные noninteractive проверки, сохраняет фактические результаты.
audit-synthesisПолучает проверенные отчёты порциями, объединяет корневые причины и сохраняет серьёзные доказанные замечания без голосования большинством.

Все шесть — Luna/medium. Четыре статических трека не получают bash и инструменты редактирования. Executor получает bash, но контракт запрещает намеренные изменения исходников, install/update, formatter-fix, сетевые мутации и Git-мутации. Shell — доверенная граница, а не абсолютная гарантия отсутствия побочных файлов.

  1. Audit: параллельные contributors

    Одинаковый ограниченный контекст задачи и Git-состояния. Отчёты изолированы друг от друга. Executor начинает с дешёвых проверок; для standalone и feature final-audit должен затем выполнить объявленные полные noninteractive test suites. Невозможность проверки записывает как unproven, а не выдумывает команду.

  2. Первый валидный отчёт активирует synthesis

    Пока синтезатор занят, новые отчёты складываются в очередь. На следующем свободном ходе передаются одним пакетом. Каждый источник интегрируется ровно один раз; занятый синтезатор не прерывают.

  3. Все пять интегрированы → финальный отчёт

    Контроллер проверяет структуру, канонизирует данные executor и назначает finding IDs вида AUD-001. Итог содержит findings, конфликты и непроверенное, но не readiness verdict.

Initial: задача и optional acceptance_criteria. Closure: prior_blockers с условиями закрытия, remediation_diff и touched_invariants; проверяются только заданные блокеры и затронутые инварианты, а не заново весь мир.

Коррекция: неправильному или отсутствующему отчёту дают до трёх дополнительных ходов в той же сессии. Для синтезатора бюджет общий на все порции. Ошибка провайдера или отмена — не такая коррекция, run завершается с ошибкой. Автоматического исправления кода в standalone audit нет.

08 / где действительно стоят ограничения

Не всё здесь «параметры». Большая часть — внутренняя политика.

Публичное поле Сейчас Оценка упрощения
pipeline_name Обязательно: 3–5 lowercase kebab-case слов, до 64 символов, без нормализации. Контроллер добавляет 8 hex символов. Самый очевидный декоративный барьер. Можно генерировать ID и принимать необязательную произвольную подпись.
pipeline Выбор четырёх графов; если не передан, запускается feature. При депрекации обязательно убрать опасный default. Не перенаправлять молча в другой граф.
task / working_dir Смысл задачи и рабочая область. Для implementation нужен точный подготовленный linked root. Не псевдопараметры. Сохранить явную рабочую область; автосоздание workspace — отдельное изменение владения.
git_commit Feature требует true; small допускает false; plan/audit отвергают true. В feature это подтверждение права, а не настройка. При новом API право можно выразить видом операции; просто сделать implicit true — расширение полномочий.
worktree_root / worktree_prepare Обязательны для feature; второй — упорядоченные команды подготовки детей. Уйдут вместе с внутренней машиной ветвей. В живом старом feature удалять нельзя без замены подготовки и размещения.
plan_path Обязательно у plan; null либо безопасный путь внутри workspace. Можно default=null. Проверки границ реального пути оставить.
audit Только standalone audit; initial/closure и типизированные сведения о блокерах. Содержательная граница scope, не декоративная формальность. Особенно полезна против бесконечного повторного аудита.
wallclock_limit Опционально, 30s–24h, одно целочисленное обозначение. Без параметра общего stage deadline нет. Уже выключен по умолчанию. Удаление почти не снимает рабочих барьеров; важнее честно назвать область действия.

Время, повторы и завершение

  • Stage deadline предупреждает на 80%, на 100% завершает со статусом limited. У feature динамические plan/build/review не имеют этой stage-таймизации; она остаётся у discovery и audit-части.
  • pipeline_child_wait исключён из обычного трёхминутного tool timeout. Отмена и включённый stage deadline продолжают действовать.
  • Discovery / planning / общий audit: начальный ответ + до трёх коррекций контракта. Feature task: четыре попытки, каждая новой Luna-сессией. Это разные бюджеты.
  • completed, failed, cancelled, limited — состояния исполнения. Отдельные implementation/execution acceptance — отчётные проекции, не дополнительные полномочия на merge.
  • Перезапуск или disposal сессии не возобновляет run из артефактов. Сохранившиеся JSON и ветви — диагностика, а не checkpoint для resume.

Что защищает sandbox feature

Агент и проверки ограничены назначенным worktree, сеть отключена, живая Git-метаинформация закрыта. Подготовка окружения — отдельный режим с сетью и writable package caches. Коммиты, ветки и cherry-pick принадлежат контроллеру. Проверкам доступен подготовленный read-only Git snapshot; точная команда git diff --check имеет отдельный контроллерный маршрут. Это не просто инструкция модели «не трогай Git».

09 / «в гите — готово, остальное удаляем»

Да — как правило сохранения результата.
Нет — как доказательство качества.

Нужно определить «в Git» как в принятом коммите, а не tracked/staged и не любой provisional HEAD. Коммит сохраняет байты; прохождение проверок сохраняет основание считать задачу выполненной.

Что уже делает реализация

cleanupAfterCommit восстанавливает невыбранные tracked/staged изменения из HEAD и удаляет незащищённые nonignored untracked пути. Но сохраняет preparation baseline и pending preparation paths, ограничивает удаление 2048 entries, не вычищает вложенные Git repositories/метаданные. Неудалённые остатки превращаются в warnings и residualPaths; tracked residuals дополнительно получают fingerprints.

Подготовка может изменить tracked source. Поэтому первый worker обязан явно распределить такие пути по commitPaths или discardPaths. Их отсутствие в ответе сейчас блокирует финализацию, вместо молчаливого удаления. Проверки после provisional commit тоже могут загрязнить tracked файлы и не дать принять результат.

Как выглядел бы более простой контракт — предложение

  1. Только disposable worktree, принадлежащий запуску. Не применять общий delete к checkout пользователя, соседним worktrees и их служебным файлам.
  2. Результат задачи — принятый commit SHA + итог обязательных checks. Staged и dirty файлы сами по себе результатом не являются; provisional commit ещё не равен accepted.
  3. После приёмки граница чистая. Не переносить residual state в следующую задачу. Либо привести disposable workspace к принятому коммиту, либо пересоздать его. Ошибка очистки означает проблему workspace, а не ещё один вид наследуемого состояния.
  4. Окружение имеет срок жизни. node_modules, ignored builds и caches можно сохранять, пока workspace жив, либо удалять вместе с ним и снова готовить. Удалить вообще всё ignored после каждого шага — значит сломать подготовку и платить install/build заново.
  5. При ошибке — явная политика. Сохранить refs/артефакты диагностики или уничтожить disposable workspace. Не считать случайный последний HEAD успешно законченной задачей.
Что действительно можно убрать при таком контракте: перенос tracked residuals между задачами, fingerprints этих остатков, часть preparation commit/discard bookkeeping, отдельную историю их полномочий. Что останется: checks, привязка результата к SHA, владение workspace, защита от symlink/path escape и от удаления чужой Git-метаинформации.

Резко сократить безопасную очистку проще удалением всего принадлежащего run disposable worktree, чем универсальным «почистим любые файлы». Никакие удаления по этому предложению сейчас не выполнялись.

Приоритет Изменение Цена / оговорка
Сначала: продуктовая развилка Закрыть новые запуски старого feature; убрать его как default. Отдельно остановить Luna-реализацию small-feature и использование luna-worker. Существующие run IDs и артефакты ещё должны читаться. Running-процессы используют загруженный код; изменение исходников их не переписывает.
Легко: API-косметика Убрать требование 3–5 слов в pipeline_name; сделать plan_path необязательным с null по умолчанию. Обновить schema, инструкции и контрактные тесты. Реальный canonical ID и безопасную запись файла сохранить.
Легко: устаревшая терминология Исправить Luna/xhigh в итоговом отчёте plan; убрать обещание «аудированного плана», если отдельного аудита нет. Названия legacy-файлов вроде sol-review.json сами по себе не означают запуск Sol. Переименование артефактов требует учёта читателей.
Средне: меньше разговорных посредников Для нового простого implementation-процесса убрать отдельный LLM-координатор, если тот лишь последовательно вызывает фиксированные инструменты. Так уже устроены части plan/audit. В feature Luna-root ещё и исправляет код, поэтому это не безболезненное удаление сессии.
Архитектурно: одна проверка исходной среды Заменить точное совпадение excerpt/command и повторную связь baselineChecks с readiness на один контроллерный результат preflight, привязанный к среде и коммиту. Не отменять сам baseline и повторные checks после изменений. Подготовленные дети могут отличаться от родительского окружения.
Архитектурно: commit-only результат Чистая граница между задачами вместо наследования residuals и их fingerprints. Только disposable run-owned workspace; учесть ignored environment и диагностические данные. Это не маленький флаг.
Если старый feature всё-таки жить будет Обсудить одного планировщика вместо двух кандидатов + синтеза; один независимый аудит вместо предварительных четырёх треков + финальных шести сессий. Это сокращает избыточность и стоимость, но меняет качество процесса. После правок нужна ограниченная closure-проверка затронутого, а не ещё один полный аудит.
Не делать «по пути» Не снимать sandbox, ownership, path/symlink guards, cancellation, привязку checks к коду и изоляцию аудиторов. Эти механизмы защищают состояние и достоверность. Их удаление не эквивалентно отказу от бюрократии.

Минимальное направление после депрекации

Главный агент → при необходимости plan → выбранный не-Luna исполнитель → audit → исправление главным/исполнителем → узкая closure-проверка при блокерах → решение главного агента.

Это предложенная схема ответственности, не новый зарегистрированный pipeline. Модель исполнителя здесь намеренно не выбрана за пользователя.

Если буквально запрещать Luna писать код, одних названий профилей недостаточно: прямой запуск с явным model: gpt-5.6-luna и произвольный workflow тоже могут выдать ей implementation-задачу. Следует решить, нужен ли организационный запрет в маршрутизации или технический read-only режим всех Luna. Последний — отдельная, более широкая работа.

Мой выбор: не тратить усилия на ослабление внутренностей старого feature перед его отключением. Сначала зафиксировать судьбу двух implementation-пайплайнов; затем сохранить простые read-only plan/audit и убрать только реальные помехи в их API.
