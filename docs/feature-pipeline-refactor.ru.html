Pipi / обсуждение рефакторинга / 12 точек упрощения

Граф оставляем.
Хрупкость убираем.

Astra доводит задачу до результата. Harness управляет рабочими областями, зависимостями и границами полномочий — не превращает каждую рабочую ошибку в провал pipeline.

Не отключение featureБез отказа от fork / joinБез субагентов в этой сессии

Предложения по результатам предыдущего разбора исходников. В исходниках реализована только маршрутизация пишущих feature-ролей на Astra/low; runtime не установлен, живой провайдер не проверялся. Остальной harness/recovery-рефакторинг не реализован. «Сейчас» описывает разобранные механизмы, а не утверждает, что каждый отказ инструмента немедленно завершает весь запуск.

01 / основная идея

Не отменять ошибки.
Дать исполнителю их исправлять.

Astra — исполнитель

Подготовка окружения, реализация, генерация, проверки, локальные коммиты и исправления. Обычные неудачи возвращаются в ту же сессию.

Harness — диспетчер

Выделяет рабочие области, запускает готовые задачи, объединяет ветви и записывает фактические результаты. Блокирует опасную операцию, а не любую неожиданность.

Luna — исследователь и аудитор

Собирает контекст и независимо проверяет результат. Пишущие роли большого feature переведены на Astra/low только в исходниках.

Нормальная рабочая ситуация ≠ ошибка реализации ≠ нарушение границ.

Генерация изменила файл — разобраться. Тест упал — исправить. Потеряно владение рабочей областью — приостановить опасные операции и передать вопрос наверх.

02 / целевой процесс

Ошибка возвращает к работе, а не к старту.

Стрелки ниже обозначают передачу результата следующему участнику. Рамка «возврат» — продолжение той же Astra-сессии, а не создание нового агента.

  1. Harness выделяет задачу и workspace

    Есть цель, база Git, зависимости и критерии. Идеально подготовленное окружение больше не обязательное условие старта модели.

  2. Astra готовит среду и реализует задачу

    Может устанавливать зависимости, генерировать файлы, собирать, проверять и сохранять небольшие локальные коммиты в своей области.

  3. Проверки возвращают факты

    Отдельно: exit code, вывод, проверенный вход и изменения файлов. Успешная команда не становится «упавшей» только из-за генерации.

    Есть исправимая проблемаТа же Astra получает диагностику и продолжает. Потомки задачи ждут; независимые ветви могут работать.
    Критерии выполненыAstra завершает коммиты и разбирает остатки. Harness принимает диапазон коммитов и результаты проверок.
    ↶ Возврат к работе: исправление → нужные повторные проверки → принятие результата. Не бесконечно: отсутствие прогресса, лимит или отмена приводят к остановке с сохранением сделанного.

  4. Join → review → независимый audit

    Конфликты и дефекты интеграции исправляет Astra. Успешный коммит сам по себе не доказывает качество и не разрешает push или deployment.

03 / по ходу выполнения

Двенадцать мест, где можно упростить жизнь.

01

Подготовка: модель должна получить шанс

Сейчас

Ошибка worktree_prepare останавливает новые старты до запуска исполнителя. Неуспешный baseline или изменение tracked-файлов на этом шаге тоже блокирует граф.

Предлагаем

Запускать Astra с диагностикой. Пусть изучит инструкции, установит зависимости, соберёт workspace-пакеты и поправит рецепт подготовки. Удачный рецепт повторять в дочерних копиях, разрешая его корректировать.

Граница: подготовка внутри своей рабочей области, не произвольная перенастройка системы или production.feature-graph-executor.ts · prepareBranch / executeRuntime
02

Изменённые сборкой файлы — не failed check

Сейчас

Условие passed требует одновременно exitCode = 0 и отсутствия changedPaths. Успешная команда с изменениями записывается как failed. В задаче возможны повторы; на стартовом baseline модель ещё не запущена.

Предлагаем

Разделить исход команды и побочные изменения. Отдать Astra diff: принять generated-файлы, удалить временный вывод или исправить генерацию. Повторять проверки, которые затронуты последующими правками.

Не попасть в цикл: сборка с новым номером версии при каждом запуске не обязана когда-либо дать нулевой diff. Нужно записывать проверенный вход и полученные артефакты, а не требовать неподвижности файлов.feature-task-runtime.ts · статус FeatureCheckResult
03

Readiness: диагностика вместо раннего тупика

Сейчас

Readiness-команда может завершить run ещё на discovery. Источник команды проверяется по точному excerpt; baseline-команды связаны с успешными readiness-записями.

Предлагаем

Discovery сообщает факты. Неисправная среда становится работой Astra. Источник команды остаётся объяснением, но точное совпадение текста не должно запрещать исправление команды по реальному проекту.

Сохранить: исходный baseline нужен, чтобы отличать старые падения от новых регрессий. Не превращать «проверка не запустилась» в «всё прошло».controller.ts · planning readiness
04

Коммиты: небольшие точки сохранения

Сейчас

Один provisional commit задачи и его amendments. HEAD должен совпадать с ожидаемым контроллером; другое значение считается выходом за его владение.

Предлагаем

Разрешить несколько локальных коммитов. Результат задачи — диапазон от базы до принятого HEAD. Допустимое продолжение собственной ветки не считать аварией; join переносит диапазон.

Решение ещё нужно: обычный Git или scoped Git-инструмент. Нельзя открыть push и операции над общими refs просто как побочный эффект разрешения commit.feature-task-runtime.ts · assertActive / finalize
05

Один staging вместо трёх систем выбора

Сейчас

Git index, точные commitPaths и отдельные preparation commit/discard selections дублируют выбор файлов. Неучтённый staged-путь или preparation-файл блокирует финализацию.

Предлагаем

В полностью принадлежащем задаче workspace Astra управляет обычным diff/index и коммитами. Финализация принимает результат, а не требует повторно описывать staging через ещё один контракт.

Не означает: автоматически добавить все файлы через git add -A. Исполнитель должен проверять состав коммита, исключать секреты и постороннее.feature-task-worktrees.ts · selection validation / finalization
06

Не наследовать бухгалтерию грязных остатков

Сейчас

Остатки после cleanup переносятся дальше. Tracked residuals получают fingerprints; изменение такого остатка вызывает отказ «вне владения контроллера».

Предлагаем

Dirty-файлы нормальны во время работы. Перед передачей задачи Astra завершает коммиты и разбирает остатки. Если принадлежащий run workspace нельзя очистить — сохранить принятый результат и пересоздать область.

Сохранить: ignored зависимости и кеши в живом workspace; не удалять чужие файлы. «В коммите» означает сохранено, а не автоматически проверено.feature-task-worktrees.ts · cleanupAfterCommit / residual fingerprints
07

Проверяем поведение, а не верность угаданной команде

Сейчас

Task-check вызывается по заранее объявленному checkId. Неизвестная проверка отвергается этим инструментом, даже если исходный план не предусмотрел нужную команду.

Предлагаем

План задаёт, что требуется доказать, и рекомендует команды. Astra может добавлять проверки и исправлять команды; контроллер сохраняет фактически выполненное и основания изменения.

Граница: заменить несуществующий script настоящим — нормально. Заменить упавший тест на echo ok — не выполнение критерия.feature-task-runtime.ts · checksById / host.check
08

Одна Astra-сессия на задачу

Сейчас

До четырёх попыток, каждая — новая Astra/low. Ветка, dirty-файлы и provisional commit сохраняются, но контекст исполнителя собирается заново.

Предлагаем

Постоянная Astra-сессия. Отказы инструментов и тестов возвращаются ей как рабочая диагностика. Новая сессия — при технической потере старой или исчерпании контекста, а не после каждой неудачи.

Без бесконечности: нужны понятные пределы ресурсов и реакция на отсутствие прогресса. Конкретные бюджеты ещё не выбраны; wallclock_limit сохраняется.feature-graph-executor.ts · MAX_TASK_ATTEMPTS / runSession
09

Проблемная ветка не должна замораживать независимые

Сейчас

Терминальная ошибка устанавливает общий launchingStopped. Выполняющийся сосед ещё может закончить, но новые задачи больше не запускаются.

Предлагаем

Блокировать потомков проблемной задачи, продолжать независимые ветви. Сначала локальный ремонт Astra, затем вопрос планировщику о корректировке оставшегося графа.

Глобальная остановка: отмена, общий лимит или реальная общая проблема. Один неподготовленный пакет сам по себе не общая авария.feature-graph-executor.ts · launchingStopped / terminalError
10

Join: сохранить механизм, усилить ремонт

Сейчас

Есть отдельный conflict resolver и join-repair при семантической ошибке интеграции. Это полезная часть графа, но её исполнители и операции ограничены старым task-контрактом.

Предлагаем

Astra разрешает конфликты и исправляет интеграцию с обычными возможностями подготовки, проверок и нескольких коммитов. Ошибки среды отделяются от дефектов объединённого кода.

Дополнительно: разрешить планировщику поправить ещё не запущенные задачи, если декомпозиция оказалась неверной. Не переписывать произвольно уже выполняющиеся ветви.feature-graph-executor.ts · joins и repair
11

Шире полномочия внутри, яснее границы снаружи

Сейчас

Подготовка и обычное выполнение имеют разные сетевые права. Feature sandbox закрывает живую Git-метаинформацию; часть нормальной работы приходится выражать специальными инструментами.

Предлагаем

Дать исполнителю установку зависимостей, генерацию, форматирование, сборки, нужные проверки и локальные коммиты. Для сети и процессов сделать понятные полномочия, достаточные для этой работы.

Остаётся закрытым: чужие workspaces, произвольные credentials, push и deployment без отдельного разрешения. Отказ должен объяснять границу, а не заставлять модель угадывать обход.feature-sandbox.ts · filesystem / Git / network boundaries
12

Контракт управления — строгий. Описание — проще.

Сейчас

Структурированные отчёты имеют бюджеты коррекций. Их исчерпание может закончить run. Размеры и служебные требования создают дополнительные причины отказа.

Предлагаем

Оставить строгими IDs, зависимости, статусы и ссылки на результат. Сократить требования к описательным полям. Безопасно нормализовать порядок и дубли; большие материалы выдавать частями.

Различать: ошибка оформления, ошибка сохранения диагностики и дефект кода — разные события. Потеря критичного состояния контроллера всё же требует остановки опасных операций.controller.ts · submission corrections / evidence persistence
04 / не всякая ошибка — конец запуска

Кому возвращается проблема?

Событие Реакция Что продолжается
Неверный аргумент инструмента Диагностика в ту же Astra-сессию; исправление вызова. Текущая задача.
Сборка изменила файлы Показать diff; выбрать нужные изменения и проверки. Текущая задача; это не автоматический failed check.
Нет зависимостей / тест упал / конфликт Подготовка или ремонт исполнителем. Независимые ветви; потомки ждут принятого результата.
Нет прогресса в задаче Зафиксировать блокировку и передать вопрос планировщику или главному агенту. Независимые ветви в пределах общего бюджета.
Потеря владения Git / чужой путь Приостановить опасную операцию, сохранить диагностику, передать наверх. Только доказуемо незатронутая работа.
Отмена / исчерпанный лимит Остановиться, сохранить принятые и промежуточные результаты. Не запускать новые работы вопреки отмене или лимиту.

Это предлагаемая политика, не перечень уже существующих статусов API. Возобновление после завершения процесса — отдельная задача, здесь оно не обещается.

05 / договорённости и открытые решения

Не тратить рефакторинг на косметику.

Оставляем

  • Граф, fork / join.
  • pipeline_name как есть.
  • Явный task / working_dir.
  • Обязательный plan_path.
  • wallclock_limit.
  • Независимый аудит.

Меняем по сути

  • Подготовка — работа модели.
  • Больше локальных коммитов.
  • Ошибки — сначала исполнителю.
  • Astra вместо Luna в пишущих feature-ролях.
  • Меньше дублирующих контрактов.

Ещё обсуждаем

  • Явный выбор pipeline без неявного default.
  • Перенос сложного audit-входа в task при структурированном выходе.
  • Как скрыть размещение и подготовку worktrees за управлением workspace.
  • Точные права Git, сети и бюджеты восстановления.

Поправка к первой странице: feature не депрекейтим. Поэтому worktree_root и подготовка дочерних worktrees не исчезают автоматически: графу всё ещё нужны изолированные рабочие копии. Упростить нужно их обслуживание и публичный интерфейс, а не саму изоляцию.

Распределение моделей: статус исходников

Роль Модель Статус
Discovery, статический audit, executor и synthesis Luna / medium Сохраняем исследование и независимую проверку.
Feature planning и final review Astra / low Уже описано в текущем feature-контракте.
Feature tasks, conflict resolver, join-repair, remediation Astra / low Реализовано в исходниках с явным low, включая post-review audit/remediation root и его same-session final remediation. Lifecycle не изменён; runtime не установлен, live-проверки нет.
Small-feature implementer Astra / low По переданному итогу соседней ветки уже изменён и установлен. Координатор и четыре аудитора — Luna/medium. Здесь повторно не проверялось.
06 / порядок работ для обсуждения

Сначала исправить самые дорогие отказы.

  1. Astra во всех пишущих feature-ролях.
    Не перепутать исполнителей с исследователями и аудиторами.
  2. Разделить исход проверки и изменения файлов.
    Устранить конкретную проблему генерации и версий сборки.
  3. Передавать preparation / baseline ошибки модели.
    Дать подготовить и починить среду до терминального решения.
  4. Постоянная сессия и несколько коммитов.
    Изменить контракт задачи и перенос её результата через join.
  5. Упростить финализацию и убрать residual-бухгалтерию.
    Ясная граница принятого результата вместо множества исключений.
  6. Локализовать сбои по ветвям.
    Независимая работа не должна останавливаться из-за одного исправимого узла.
Цель — не pipeline, который всегда зелёный.

Цель — pipeline, который позволяет умной модели решить обычные проблемы, сохраняет сделанное и останавливается только по содержательной причине.

Это объяснение направления, а не готовый проверенный план миграции. При реализации понадобятся отдельные контракты и тесты переходов состояния; ни sandbox, ни проверки результата здесь фактически не ослаблялись.

Исходники для следующего разбора

  • feature-task-runtime.ts — checks, attempt, finalize, HEAD.
  • feature-task-worktrees.ts — paths, staging, cleanup и residuals.
  • feature-graph-executor.ts — preparation, retries, ветви, joins.
  • controller.ts — readiness, отчёты, этапы и результаты.
  • feature-sandbox.ts — границы полномочий.
  • Первая архитектурная раскладка — исторический снимок до уточнения цели; её предложения об отключении feature и модель small-feature уже не отражают новое направление.
