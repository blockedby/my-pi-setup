Pipi profile inheritance / implementation drawing

Make every child load Pipi

The goal is not to replace the Pi engine. The goal is to make the main session and every child load Pipi's profile instead of regular Pi's profile.

1

Profile

What does “load Pipi” mean?

Use the Pipi folders, packages, authentication, and sessions while running the shared Pi engine.

pipi is a launcher. It is not a second agent engine. It selects a profile and then executes Pi. Therefore, “Pipi loads Pipi” means that every session resolves ~/.pipi, not ~/.pi.

2

Minimal implementation plan

Only the outer launcher selects Pipi. Child code confirms and inherits that selection.

01

Mark the launcher

Keep the existing two isolation variables and add one clear marker. This lets extensions distinguish Pipi from regular Pi without checking hard-coded home paths.

export PIPI_PROFILE=1 export PIPI_CODING_AGENT_DIR="$HOME/.pipi/agent" export PIPI_CODING_AGENT_SESSION_DIR="$HOME/.pipi/sessions" export PI_CODING_AGENT_DIR="$HOME/.pipi/agent" export PI_CODING_AGENT_SESSION_DIR="$HOME/.pipi/sessions" exec "$HOME/.pipi/agent/npm/node_modules/.bin/pi" "$@"
02

Launch the root with Pipi

The setup command installs the wrapper. The user then opens the root session with pipi, not regular pi.

npm run install:pipi pipi
03

Resolve child resources from the active profile

Keep child creation in process. Build its settings manager and resource loader from getAgentDir(). Under Pipi, this resolves ~/.pipi/agent.

const agentDir = getAgentDir() const settings = SettingsManager.create(cwd, agentDir) const loader = new DefaultResourceLoader({ agentDir, settings })
04

Fail closed for Pipi-only nesting

Before exposing nested spawning, require the profile marker and expected active directory. If regular Pi loads the fork accidentally, keep nesting disabled and show a clear reason.

if (process.env.PIPI_PROFILE !== "1") { disableNestedSpawn("Start this setup with pipi") }
5

Why not execute Pipi again?

Design Result Decision
Root runs pipi; children use createAgentSession() One process, one manager, one concurrency limit, and one navigable TUI. Use this
Every child executes pipi as a subprocess Separate managers and lifecycle trees. Root cancellation and TUI navigation become unreliable. Avoid
Root starts regular pi, then code hopes to find Pipi resources Ambiguous profile selection and possible use of ~/.pi/agent. Fail closed
The short answer: the command name is important only at startup. After startup, profile inheritance is more important than launching another command. Run pipi once; create every Pi child inside that Pipi-configured runtime.

The finished shape

terminal
└── pipi
    ├── selects ~/.pipi/agent
    ├── selects ~/.pipi/sessions
    ├── starts the Pi engine once
    └── shared SubagentManager
        ├── main Pipi session
        ├── Pi child — Pipi profile
        │   └── nested Pi child — Pipi profile
        └── Pi child — Pipi profile

The engine remains Pi. The product experience, resources, storage, manager, and TUI remain Pipi.
